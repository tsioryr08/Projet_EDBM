1. OBJECTIF GENERAL
-------------------

SociéTech est une application web PHP destinee a accompagner la creation
et le suivi juridique de societes malagasy. Elle fournit :

- un parcours de creation de societe ;
- le choix de la forme sociale ;
- la saisie des informations de la societe ;
- la saisie des associes et des dirigeants ;
- la creation automatique d'un dossier ;
- une checklist des pieces requises ;
- le suivi du statut du dossier ;
- la planification et la tenue de reunions et assemblees ;
- le calcul du quorum, des majorites et des resultats de vote ;
- la generation de documents PDF ;
- la gestion des convocations, proces-verbaux et documents constitutifs ;
- des regles metier stockees en base pour eviter de coder les regles juridiques
  directement dans les vues ;
- un acces protege au dossier de chaque societe par mot de passe.

Le projet est une application CodeIgniter classique, avec une separation
Controllers / Models / Libraries / Views / Migrations / Seeds.

La page affiche :

- le bouton "Telecharger les statuts".

Le lien "Ouvrir le dossier" pointe vers /dossiers/{id}. Cette route est
protegee par le controleur Dossiers et redirige vers l'ecran de mot de passe

4.3 Formulaire de creation

Route :

    GET /societes/nouveau
    POST /societes

Controleur :

    app/Controllers/Societes.php

Methodes :

- new() : affiche le formulaire ;
- create() : valide et enregistre la societe ;
- saveRows() : enregistre les associes et dirigeants envoyes en tableaux.

Vue :

    app/Views/societe/form.php

Le formulaire contient :

- type_societe_id ;
- denomination ;
- mode_administration pour les SA ;
- siege ;
- objet ;
- capital ;
- duree_annees ;
- code_activite ;
- activite_reglementee ;
- les associes ;
- les dirigeants ;
- mot_de_passe ;
- mot_de_passe_confirmation.

Validation du formulaire :

- type_societe_id requis et numerique ;
- denomination requise, longueur maximale 150 ;
- siege facultatif, longueur maximale 255 ;
- capital facultatif et decimal ;
- duree_annees facultatif et entier naturel ;
- mot_de_passe requis, minimum 8 caracteres, maximum 72 ;
- mot_de_passe_confirmation obligatoire et identique au mot de passe.

Protection du mot de passe :

- le mot de passe n'est jamais stocke en clair ;
- Societes::create() utilise password_hash(..., PASSWORD_DEFAULT) ;
- SocieteModel autorise le champ mot_de_passe ;
- la colonne est VARCHAR(255) pour stocker le hash.

Ordre de creation :

1. validation du formulaire ;
2. ouverture d'une transaction ;
3. insertion dans societe ;
4. insertion du dossier associe avec le statut brouillon ;
5. insertion des associes ;
6. insertion des dirigeants ;
7. evaluation des regles de creation ;
8. rollback si une regle bloquante est rencontree ;
9. commit ;
10. redirection vers /dossiers/{id}.

Si une vue est retournee en cas d'erreur, create() est declaree :

    public function create(): string|ResponseInterface

Cette union est necessaire car CodeIgniter accepte soit une chaine HTML
retournee par view(), soit une reponse HTTP.

4.4 Acces protege au dossier

Routes :

    GET  /dossiers/{id}/acces
    POST /dossiers/{id}/acces

Controleur :

    app/Controllers/Dossiers.php

Methode :

    Dossiers::access()

Vue :

    app/Views/dossier/access.php

La vue affiche :

- "Acces securise" ;
- le nom de la societe ;
- un seul champ mot_de_passe ;
- un bouton "Ouvrir le dossier" ;
- un bouton "Retour".

La confirmation du mot de passe est demandee uniquement pendant la creation
de la societe. Lors de l'ouverture du dossier, un seul mot de passe est
demande.

Le traitement POST utilise explicitement :

    $this->request->getMethod(true) === 'POST'

Cette forme est importante avec la version de CodeIgniter utilisee, car
getMethod() peut retourner la methode dans une casse differente.

Verification :

    password_verify($motDePasse, $societe['mot_de_passe'])

En cas de succes, la session contient :

    societe_access_{id} = true

Puis l'utilisateur est redirige vers /dossiers/{id}.

Dans Dossiers::show(), l'acces est refuse si cette cle de session est absente :

    if (! session()->get('societe_access_' . $societeId)) {
        return redirect()->to(site_url('dossiers/' . $societeId . '/acces'));
    }

Ainsi, un utilisateur ne peut pas contourner l'ecran en saisissant
directement l'URL du dossier.

Attention aux anciennes societes :

- les societes creees avant l'ajout de la fonctionnalite peuvent avoir
  mot_de_passe NULL ;
- aucun mot de passe ne peut etre valide si le hash est absent ;
- une nouvelle fonctionnalite de reinitialisation pourra etre ajoutee plus
  tard si necessaire.

11. SECURITE ET VALIDATION DES ENTREES
--------------------------------------

CSRF :

- les formulaires HTML utilisent csrf_field() ;
- la protection CSRF est configuree dans Security.php ;
- le formulaire d'acces, le formulaire de creation et les formulaires de
  Vie de Société sont proteges.

Echappement :

- les sorties HTML utilisent principalement esc() ;
- les vues PDF utilisent htmlspecialchars() ou les helpers adaptes.

Mot de passe :

- password_hash() a l'enregistrement ;
- password_verify() a l'ouverture ;
- jamais de comparaison directe avec le hash ;
- jamais de stockage du mot de passe en clair.

Transactions :

- la creation d'une societe et de son dossier est transactionnelle ;
- une erreur bloquante provoque un rollback ;
- le dossier ne doit pas etre valide si les regles de creation bloquent.

Validation :

- validation CodeIgniter dans les controleurs ;
- contraintes SQL dans les migrations ;
- regles juridiques dans regle_validation, regle_delai et regle_quorum ;
- les regles non verifiees peuvent etre signalees comme avertissements ou
  "a confirmer".

Correction de la regle duree_max :

Le seeder contenait la regle, mais une base existante pouvait avoir la table
regle_validation sans la ligne duree_max. La migration
EnsureDureeMaxValidationRule ajoute donc automatiquement cette ligne si elle
manque.

15. POINTS D'ATTENTION POUR LA MAINTENANCE
------------------------------------------

- Toujours lancer php spark migrate apres l'ajout d'une migration.
- Ne pas supprimer ou modifier manuellement les anciens hashes sans sauvegarde.
- Pour une societe ancienne sans mot_de_passe, prevoir une procedure de
  reinitialisation ou une migration de reprise.
- Ne pas afficher le hash dans une vue ou un log.
- Ne pas utiliser password_hash deux fois sur un mot de passe deja hashe.
- Conserver password_verify pour les connexions.
- Toute nouvelle route de dossier doit aussi verifier la session si elle expose
  des donnees privees. Actuellement la protection centrale est explicite dans
  show(); les autres actions de dossier doivent etre auditees si elles sont
  exposees directement.
- Garder les regles metier en base quand elles sont configurables ou soumises
  a confirmation juridique.
- Utiliser les services existants plutot que de reproduire les calculs dans
  les controleurs ou les vues.
- Toujours echapper les donnees affichees avec esc().
- Toujours inclure csrf_field() dans les formulaires POST.
- Tester les nouveaux parcours avec une base contenant les migrations et les
  seeds a jour.
